# Bootloader Unlock Feasibility

## Device and observed state

- Device: ASUS Zenfone 10, model `ASUS_AI2302`
- Android/build: Android 15, `WW_35.0604.0404.165`
- Android security patch: `2026-08-05` (matches the ASUS release note for this build)
- Bootloader: `0.0.024.0-WW-user` (`version-bootloader`; `version` is unavailable)
- OEM unlocking option: unavailable (reported by the owner)
- Read-only bootloader Fastboot results: `is-userspace=no`, `unlocked=no`, `secure=yes`, `flashing get_unlock_ability=0`, `partition-size:frp=0x80000` (512 KiB).

The device is currently locked. The user verified bootloader Fastboot with `is-userspace=no`; that mode reports `get_unlock_ability=0`. The earlier rejected requests were made in `fastbootd` and do not count as unlock attempts by the bootloader. No unlock, flash, erase, or downgrade operation succeeded.

## Evidence and limits

Android documents `fastbootd` as separate from bootloader Fastboot. Once switched to bootloader Fastboot, this device reported `get_unlock_ability=0`. Android's bootloader guidance says devices should deny the standard unlock operation unless `get_unlock_ability` is `1`; therefore the standard unlock path is denied in the observed state.

ASUS stated on ZenTalk that its unlock tool has been discontinued for phone models released in 2023 or earlier. The Zenfone 10 falls in that group. ASUS does publish a Zenfone 10 kernel source package for version `35.0604.0404.165`, matching this device's build. That listing is for kernel source; it does not establish that bootloader source, signing material, or an unlock authorization service is available. ASUS's firmware page also says downgrading is not possible after the listed update.

## Assessment

**Standard unlock client: denied by the bootloader's reported permission.** The guarded client refuses when `get_unlock_ability=0`. Separately, this ABL registers an `oem asus-unlock` handler that verifies a token before continuing. A valid token and its current availability have not been established, so this finding is not yet a usable unlock method.

**The two unlock routes are gated by different state and are decoupled.** Disassembly shows `get_unlock_ability` is backed by a global `IsAllowUnlock` at `0x2cbf30`, written only by the `frp` reader `0x9e458` (bit 0 of the partition's last byte) and read back only by the `get_unlock_ability` reporter `0xa2760`; a whole-`.text` load/store cross-reference finds exactly three accesses to that global and none in the ASUS path. The `oem asus-unlock` success path (`0xa528c` → token verifier `0xaff70` → `0x1ae90`) instead sets the device-info *IsUnlocked* byte (`0x2b3eb2`) and persists the DeviceInfo structure through a Qualcomm vendor store protocol (`8e5eff91-21b6-47d3-af2b-c15a01e020ec`, write method, size `0xec8`). It never reads or writes `IsAllowUnlock` and never touches the `frp` partition. The ASUS token path is therefore an independent, signed-token-gated unlock that **bypasses** `get_unlock_ability` rather than changing it; its only cryptographic gate is the token verifier, which requires an ASUS-signed token (private key / provisioning service), not derivable from public firmware.

## Public advisory review

The Android August 2026 bulletin says patch level `2026-08-05` addresses the Android issues listed for the `2026-08-01` bulletin and earlier patch levels. AOSP also explains that chipset/vendor fixes and device-partner advisories can be separate from the Android patch-level declaration. Therefore, the patch date does not by itself establish the patch state of every proprietary boot-chain component.

Targeted searches of public ASUS, AOSP, and Qualcomm material did not find a supported unlock procedure or a public advisory that maps bootloader version `0.0.024.0-WW-user` to a specific unlock method. This does not resolve the vendor token path found in the firmware; continue static analysis to determine its requirements. No bypass has been demonstrated.

## Firmware payload inventory

The official ASUS ZIP for this exact build was checked against ASUS's published SHA-256. The OTA `FILE_SIZE`, `FILE_HASH`, `METADATA_SIZE`, and `METADATA_HASH` properties also match the embedded `payload.bin` and its metadata. This internal consistency check complements the independently published ASUS ZIP checksum. Its OTA payload manifest identifies a full payload with 37 partitions, including `abl`, `xbl`, `tz`, `boot`, `init_boot`, `recovery`, and `vbmeta`. The boot-chain summary reports `abl` target size 729,088 bytes, `xbl` 1,208,320 bytes, and `tz` 3,936,256 bytes; their payload operations are compressed replacements (`REPLACE_XZ`). This is metadata only: it does not expose source code, signing keys, or an unlock authorization. The manifest has no security-patch field, while ASUS's release page lists `2026-08-05`. The ABL partition was later reconstructed locally for static inspection; no image was written to the phone.

The `abl` image was reconstructed offline to `/tmp/zenfone10_abl.img` and its SHA-256 matched the manifest's partition hash (`8ce6dfcc5ff045f69558d9edeaa20f99aae6f19078a55749e81c05709bfd147e`). ELF inspection identifies an ELF32 ARM executable with no section table; a basic printable-string scan found no Fastboot/unlock terms. This is a limited static observation, not a conclusion about the code's behavior. The image was not executed or written to the phone.

The ABL image contains a UEFI firmware volume with a guided LZMA section. Its decompressed FV contains one `LinuxLoader` AArch64 PE32 application. Static strings in that image include authorization-related indicators (`IsAllowUnlock`, `IsAuthorized`, `IsDebugUnlocked`, and an authorized-hash failure message). This suggests vendor authorization checks are present, but strings alone do not establish their exact logic or an unlock method. No OEM command was sent to the phone; no image was patched or flashed.

An AArch64 cross-reference pass refined those observations. `IsAllowUnlock is %d` is passed to a logging helper. At PE RVA `0x9e458`, the UTF-16 string `frp` is passed to a lookup helper; on its success path, code allocates a buffer from the returned descriptor and invokes a read callback. At RVA `0x9e5a8`, it stores bit 0 of the buffer's last byte to the `IsAllowUnlock` global. The `get_unlock_ability` handler reports that global. Nearby messages include `Error Reading FRP partition` and `Failed to allocate memory for unlock value`. The callback implementation and FRP data format are not yet identified. This does not show that changing FRP data would be accepted or safe.

The Fastboot command table around PE RVA `0x106e08` maps `flashing get_unlock_ability` to handler `0xa2760`, `flashing unlock` to `0xa27b8`, and `oem asus-unlock` to `0xa528c`. The ASUS handler obtains an argument and calls verifier `0xaff70`; a nonzero return follows the `Verify unlock token fail.` branch, while the success path performs additional state checks and contains a `Device unlocked successfully.` message. The verifier's strings include `verify_RD_unlock` and `asuskey`; its call path passes a 981-byte DER block at image address `0x2b2429` through wrapper `0xafdc0`. Local OpenSSL inspection identifies that block as a self-signed ASUS X.509 certificate with an RSA 2048-bit public key and SHA-256/RSA certificate signature. Its encoded validity ended on 2023-03-29; this does not prove the bootloader checks certificate dates. A separate code path at `0xa0904` reports `Verify FRP Unlock Signature Failed!!`. This strongly suggests a signed vendor token path, but the token format, private signing-key source, current token availability, and relationship to standard `flashing unlock` remain unresolved. The bundled certificate contains a public key; it cannot produce a valid signature by itself.

Further static tracing shows that `oem asus-unlock` calls the verifier without setting a token argument at that call site. The verifier allocates a 256-byte buffer, passes the UTF-16 name `asuskey` to a lookup helper, then passes the bundled certificate to a crypto wrapper. The lookup enumerates handles supporting UEFI Block I/O and Device Path, selects hard-drive partition nodes, obtains partition metadata through an additional protocol, and compares its name field with the requested `asuskey`. It then invokes the Block I/O `ReadBlocks` method (the method at protocol offset 24) into the verifier buffer. This identifies the ABL lookup backend and ties it to the same named partition that Android's `/vendor/bin/writekey` writes. The exact authorized blob source and precise signed bytes remain unresolved. The protocol GUID and method layout were checked against the primary EDK2 Block I/O and Device Path headers; the extra partition-metadata protocol is vendor-specific.

AArch64 disassembly (capstone) resolved the generic partition-selection helper at PE RVA `0x11010`, which the verifier and ~39 other call sites use. It loads the `gBS` pointer from a global at `0x2b30a8` and calls `gBS->LocateHandleBuffer` with `SearchType=ByProtocol` and an EFI protocol GUID: `EFI_BLOCK_IO_PROTOCOL` (`964e5b21-6459-11d2-8e39-00a0c969723b`) by default, or `EFI_SIMPLE_FILE_SYSTEM_PROTOCOL` (`964e5b22-…`) when a caller access flag bit is set. For each returned handle it calls `gBS->HandleProtocol` for `EFI_DEVICE_PATH_PROTOCOL` (`09576e91-6d3f-11d2-8e39-00a0c969723b`) and a Qualcomm vendor partition-info protocol (`6848de61-eb61-4def-9a8e-3817cbeb8f1c`), then selects the partition by its name field. This is EFI-protocol-based enumeration; it does not use any GPT partition-type GUID. A whole-`.text` cross-reference scan confirms the `frp` GPT partition-**type** GUID (`91b72d4d-71e0-4cbf-9b8e-236381cff17a`) is referenced exactly once in code — at `0x277d8`, inside the FRP erase helper `0x277b0`, which copies its 16 bytes into a local partition-type match descriptor. The erase helper does not route through `0x11010`. The GPT type GUID and the EFI protocol GUIDs are therefore distinct in value, code, and purpose.

The Android-side firmware contains a local provisioning path. `system/etc/init/init.asus.unlock.rc` labels a disabled one-shot `/vendor/bin/writekey` service as the user unlock tool; a property trigger starts it. The native library `system/fake-libs64/libunlock.asus.so` exposes JNI names including `getNativeKey` and `writeNativeSign`, and references `/ADF/asuskey.bin` plus readiness properties. The vendor `writekey` executable references `/dev/block/bootdevice/by-name/asuskey` and `/ADF/asuskey.bin`, and imports file-read/write and property APIs.

Static decompilation of `DMClient.apk` (SHA-256 `cce7ee9702220f12f907d6cb20d5fe98091ea94af8bf76cc68b095ab26e1b26c`) separated two network routes that the earlier string scan could not distinguish. `HttpSyncUnlockStatus` reads `ro.boot.verifiedbootstate`, maps `green` to `0` and another nonempty value to `1`, then posts only that status to `/sync/unlock`; its success callback updates sync state and schedules another job. It does not receive or forward an unlock token. `HttpGetAsusKeybox` is separate: it uploads a report and keybox type to `/key/verify`, then passes the response's keybox field to `ASUSKeyBox2Service`. No direct call from that keybox route to the unlock Binder was found, so it must not be treated as the source of the ABL token.

The APK manifest declares `com.asus.dm.c2dm.UnlockService` exported, with Binder interface `com.asus.unlockservice.IAsusUnlockService`. Its byte-array write method writes to `/ADF/asuskey.bin`, sets `sys.debug.write.asuskey`, and waits for `vendor.debug.asuskey.ready`. The method checks the caller UID against a fixed package allowlist and compares the caller's signing identity with `com.asus.filemanager` using `PackageManager.checkSignatures`; it does not compare against DMClient. The allowlist is `com.asus.unlock`, `com.asus.openbeta2`, `com.asus.unlocktool`, and `com.asus.cn.unlock`. This confirms a protected local handoff to the vendor writer. JADX 1.5.6 reconstructed these target classes, although the overall APK pass reported 18 decompilation errors; findings above are limited to the successfully reconstructed methods. No endpoint was contacted, service/property was triggered, or device operation performed.


An exact package-name and DEX-marker scan of all 194 APKs under the reconstructed `system/app` and `system/priv-app` found only `com.asus.openbeta2` among the four Binder allowlisted packages. `DMClient` contains the service implementation, not a caller of its byte-array method. This scan did not parse every APK manifest in `product`, `system_ext`, or `vendor`; the earlier directory-name inventory there is not proof that those partitions contain no client.

The historical ASUS unlock client was found at the ASUS CDN URL linked from [this ZenTalk post](https://zentalk.asus.com/t5/zenfone-10/zenfone-10-bootload-unlock-news/m-p/432115): `AsusUnlock_1.0.0.7_210127_fulldpi.apk`, served from the `ZS673KS` directory. ASUS identifies `ZS673KS` as ROG Phone 5, so this is a cross-model archival sample, not a Zenfone 10 release. Its SHA-256 is `c0c7c38d42e3ade12c3ab9edd5cbda77736d9edc806206212c3ac30fe052e2c6`. Its signer is ASUS AMAX Key (certificate SHA-256 `9A:F9:49:7B:EC:4A:32:A8:AA:06:9D:C2:0B:0E:77:3A:86:6B:80:55:D2:AF:6B:FC:A7:7E:23:4A:3A:2B:21:93`), identical to the signer on this firmware's `com.asus.filemanager` APK. The equality explains why the historical ASUS app meets the local Binder signature check; it does not prove device/build compatibility.

Static inspection of that APK maps the old provisioning flow: it posts login data to `dm.asus.com`, then posts the device ISN, app version, and key index to `/unlock/register`. The response model supplies `Secrettoken`; the app hex-decodes it and calls `writeSignKey(byte[])`. The app's local check verifies the converted token is at least 256 bytes; the current firmware's vendor writer requires exactly 256 bytes. The legacy AIDL descriptor is the same as the current service descriptor, and both assign transaction 7 to the byte-array write. In the Zenfone 10 `DMClient.apk`, transaction 7 dispatches to `C0(parcel.createByteArray())`, which writes `/ADF/asuskey.bin` before triggering the vendor writer. Thus the historical official client reveals the intended byte source: an ASUS server response, not a value derived locally from public firmware data.

The Zenfone 10 `DMClient` routes `/key/generate`, `/key/nonce`, `/key/nonceEnc`, and `/key/verify` into its keybox/Widevine services; static call tracing found no path from those callbacks to `UnlockService.C0`. `/sync/unlock` remains status telemetry. No network endpoint was contacted. ASUS states that the unlock tool for phone models released in 2023 or earlier was discontinued from its official site ([current moderator statement](https://zentalk.asus.com/t5/zenfone-10/release-bootloader-unlock-tool-discontinuation-products-eol/td-p/500937)); this does not establish whether the server endpoint is still reachable or whether it would authorize this Zenfone 10 build. The archival APK is only evidence of the historical protocol.

Static AArch64 disassembly of `/vendor/bin/writekey` (SHA-256 `bfe0a9299cbd38017f9bfb3f55e51af71b14b417cd8522b3cdd939a8c9bbed37`) shows it reads `/ADF/asuskey.bin` into a buffer and requires exactly 256 bytes. It then opens `/dev/block/bootdevice/by-name/asuskey` in `wb+` mode, writes those 256 bytes, calls `sync`, and sets `vendor.debug.asuskey.ready=1`; it removes the input file after reading it. Its dynamic imports cover ordinary file I/O, logging, sync, and property APIs, with no crypto library dependency. Combined with the ABL's name-matched Block I/O read into a 256-byte verifier buffer, this maps both ends of the on-device provisioning path to the same partition. The historical client's server field is mapped below; no token payload or runtime transfer was captured for this Zenfone 10. The helper does not appear to perform signature verification; the ABL verifier is the relevant cryptographic gate.

Static tracing of the FRP/object path shows it reads the UTF-16 object fields `asuskey2` and `signature`, copies a 256-byte signature buffer, and calls the verifier wrapper at `0x47270` with a 51-byte data buffer. That wrapper reaches a separate EFI protocol lookup path at `0x46e30` (protocol GUID `408ec123-134e-4b80-9142-b89a0e08f8b3`). Its failure branch leads to `Verify FRP Unlock Signature Failed!!`. The OEM `oem asus-unlock` handler instead reads the 256-byte `asuskey` partition, parses the embedded 981-byte ASUS X.509 certificate, and enters the helper chain through `0xafdc0`/`0xce630`; its call path does not enter `0x47270`. These are distinct verifier entrypoints with different inputs and trust-material setup. A shared lower-level crypto implementation is still possible, but the FRP public key and exact signed-data construction remain unknown.

The FRP verifier's zero return reaches code at `0xa0e34`, which calls helper `0x277b0`; a nonzero return logs `erase frp Failed!!`. Correctly decoding the embedded EFI GUID's little-endian fields yields `91b72d4d-71e0-4cbf-9b8e-236381cff17a`, the same GUID used as the `frp` GPT partition type in a public Qualcomm bootloader image example. That cross-device example is a clue, not proof of ASUS's exact partition table. In this ABL, the helper uses the GUID while enumerating storage handles, allocates a 4,096-byte buffer, reads LBA 0, zero-fills all 4,096 bytes, then writes that block back to LBA 0. It does not call the standard Fastboot unlock handler.

The separate `get_unlock_ability` path resolves the `frp` block device, reads its `EFI_BLOCK_IO_MEDIA.LastBlock` using `BlockSize` bytes, and stores bit 0 of the buffer's final byte. Under the EDK2 Block I/O layout, this is the last byte of the partition, while the FRP helper zeros the first 4,096 bytes. Thus, for any multi-block `frp` partition, the helper does not touch the permission byte and does not set unlock ability to 1. A read-only `fastboot getvar partition-size:frp` in bootloader Fastboot returned `0x80000` (524,288 bytes = 512 KiB), read from the same ABL's GPT. The permission byte is therefore at file offset `size-1 = 524,287` regardless of EFI block size (4,096-byte blocks → `LastBlock=127`; 512-byte blocks → `LastBlock=1023`; both place the permission byte at 524,287), which lies far past the first 4,096 bytes the helper zeros. This confirms, now with the real partition extent and no block-size assumption, that the post-verifier erase-FRP path cannot change `get_unlock_ability` to 1 — a negative result, not an unlock path. No FRP command, unlock operation, or signature verification was executed on a device.

The FRP verifier selects trust material using its fifth argument: the call at `0xa08fc` passes key ID `1`, and LinuxLoader's selector at `0x45e80` maps ID 1 to an 865-byte DER certificate at PE RVA `0x121b4c`. OpenSSL parses it as a self-signed RSA-2048 certificate using SHA-256/RSA, subject `C=AU, ST=Some-State, O=Internet Widgits Pty Ltd`, valid through 2048. Its SHA-256 fingerprint is `1D:96:AE:88:3C:22:8B:D2:7B:FB:C9:2B:D9:83:7C:CE:E8:7A:F8:13:23:93:8C:6F:EC:EC:29:48:7F:9F:7D:E7`; `openssl verify -check_ss_sig` accepts it as self-signed. The certificate contains a public key, not its signing private key. This differs from the key-ID-0 `AsusUnlock` certificate and the separate certificate used by `oem asus-unlock`.

The UEFI partition hash matches the OTA manifest. Its `ASN1X509Dxe` driver installs protocol GUID `408ec123-134e-4b80-9142-b89a0e08f8b3`, which LinuxLoader locates for the FRP signature check; `VerifiedBootDxe` also references that protocol. The FRP partition-type GUID appears in LinuxLoader in the inspected firmware set. The GUID-based storage selection is now fully mapped: the generic selector at `0x11010` locates partitions through standard EFI protocols (Block I/O / Simple File System / Device Path) plus a Qualcomm vendor partition-info protocol and matches by name, while the `frp` GPT type GUID is used only as a local match value inside the erase helper `0x277b0` (see above).

For this audit, the `system`, `vendor`, `product`, and `system_ext` images were reconstructed locally from the verified full OTA and each output hash matched its payload manifest entry. `debugfs` was used read-only to inspect the filesystem and extract only the listed small files. No Android property was set, no helper was executed, and no device operation was performed. The built-in public certificate and these services do not themselves provide an authorized signing token.
