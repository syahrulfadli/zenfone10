Jalur FRP membaca field objek `asuskey2` dan `signature`, menyiapkan signature 256 byte dan data 51 byte, lalu memanggil wrapper `0x47270` → `0x46e30` yang mencari protokol EFI GUID `408ec123-134e-4b80-9142-b89a0e08f8b3`. Kegagalan menuju pesan `Verify FRP Unlock Signature Failed!!`. Jalur OEM memakai partisi `asuskey`, sertifikat ASUS X.509 981 byte yang tertanam, dan helper `0xafdc0` → `0xce630`; tidak ditemukan call langsung ke wrapper FRP. Ini membuktikan entrypoint serta input berbeda, tetapi belum mengidentifikasi trust key FRP atau menyingkirkan pemakaian primitive kripto yang sama di lapisan bawah. Efek cabang sukses belum ditelusuri penuh. Tidak ada operasi perangkat, verifikasi signature, atau perubahan FRP dilakukan.
57. Menelusuri cabang setelah verifier FRP berhasil: return nol memanggil helper `0x277b0`; jika helper gagal, ABL mencatat `erase frp Failed!!`, sedangkan return nol menuju jalur penyelesaian bersama. Pada catatan awal, byte GUID ditulis dengan urutan field EFI yang keliru (`4d2db791-e071-4cbf-...`); koreksi canonical dan alur blok dicatat pada langkah 60. Jalur ini terpisah dari handler `oem asus-unlock`. Analisis ABL saja; tidak ada perintah atau perubahan perangkat.
58. Mendekompresi image `uefi` dari OTA terverifikasi dan menemukan FFS `ASN1X509Dxe`, yang memasang protocol GUID `408ec123-134e-4b80-9142-b89a0e08f8b3` yang dipakai verifier FRP di LinuxLoader. Call FRP memberi key ID `1`; selector `0x45e80` memetakan ID itu ke sertifikat DER 865 byte pada RVA `0x121b4c`. OpenSSL mengidentifikasinya sebagai self-signed RSA-2048, SHA-256/RSA, subject `C=AU, ST=Some-State, O=Internet Widgits Pty Ltd`, berlaku sampai 2048; fingerprint SHA-256 `1D:96:AE:88:3C:22:8B:D2:7B:FB:C9:2B:D9:83:7C:CE:E8:7A:F8:13:23:93:8C:6F:EC:EC:29:48:7F:9F:7D:E7`. Ini kunci publik saja, berbeda dari cert key ID 0 dan cert handler OEM. Hash partisi cocok dengan manifest. Tidak ada signature token atau private key dibuat/dicari.
59. Mencari GUID helper erase FRP pada image boot-chain hasil ekstraksi dan firmware volume UEFI yang didekompresi; kemunculan byte tersebut ada di LinuxLoader dalam cakupan yang diperiksa. Kesimpulan saat itu bahwa semantik operasi belum diketahui diperbarui pada langkah 60 setelah call site `ReadBlocks`/`WriteBlocks` ditelusuri.
60. Melanjutkan disassembly statis ABL `LinuxLoader` (image direkonstruksi ulang, SHA-256 cocok dengan manifest OTA). Data GUID di RVA `0x104900` tersimpan sebagai byte EFI little-endian `4d2db791e071bf4c9b8e236381cff17a`, yang didekode menjadi `91b72d4d-71e0-4cbf-9b8e-236381cff17a`; contoh image Qualcomm sumber-terbuka menamai GUID canonical yang sama sebagai tipe partisi `frp` (bukti lintas-perangkat, bukan partisi GPT Zenfone 10). Helper `0x277b0` membangun filter untuk enumerasi handle dan menyiapkan buffer 4.096 byte. Jalur sukses memanggil metode pada offset `+24` dengan MediaId, LBA 0, panjang 4.096, dan buffer; wrapper `0x6b88` meneruskan fill byte 0 ke rutin `SetMem` di `0x2a6c`; kemudian metode pada offset `+32` menulis buffer itu pada MediaId/LBA 0 dengan panjang yang sama. Susunan metode/argumen cocok dengan `EFI_BLOCK_IO` ReadBlocks/WriteBlocks menurut header EDK2. Secara statis, helper mengosongkan blok pertama 4 KiB pada handle yang dipilih.

    Jalur `get_unlock_ability` di RVA `0x9e458` memakai `EFI_BLOCK_IO_MEDIA.BlockSize` (offset `+12`) untuk ukuran buffer dan `LastBlock` (offset `+24`) sebagai LBA baca; sesudah read, ia memeriksa bit 0 dari byte `BlockSize-1`. Menurut layout EDK2, ini byte terakhir pada blok terakhir partisi. Jadi untuk partisi FRP multi-blok, helper di atas tidak mengubah byte izin yang dibaca `get_unlock_ability`; ukuran/`LastBlock` partisi Zenfone 10 tidak tercantum di OTA dan masih perlu konfirmasi baca-saja. Temuan ini menutup celah analisis sebelumnya, tetapi tidak menghasilkan jalur unlock: perangkat tetap melaporkan izin 0, token resmi yang berlaku belum ditemukan, dan tidak ada perintah/tulisan perangkat yang dilakukan.

## Belum dilakukan

- Bootloader Fastboot melaporkan status terkunci dan `get_unlock_ability=0`; jalur unlock standar tidak diizinkan dalam keadaan firmware saat ini. Klien menolak nilai `0` dan tidak mengirim permintaan unlock.
- Belum dilakukan pengujian otomatis; diagnostik baca-saja sudah dijalankan oleh pengguna pada perangkat nyata.

## Langkah berikutnya

Sertifikat publik verifier FRP sudah teridentifikasi, tetapi tidak memuat private signing key. Langkah paling langsung yang masih dapat mempersempit efek FRP adalah mengonfirmasi ukuran/`LastBlock` partisi `frp` dari sumber baca-saja; OTA tidak memuat GPT. Berikutnya, periksa dukungan provisioning ASUS hanya dari sumber publik; token historis `/unlock/register` berasal dari APK lintas-model. Jangan memicu property provisioning, mengubah FRP, mem-patch image, atau mengirim perintah unlock ke perangkat.
